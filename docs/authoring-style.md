# 출제·수정 노하우 (프로젝트 공통)

검토본을 열일곱 번 고치며 사용자에게 받은 지적을 일반 규칙으로 정리한 것이다. [AGENTS.md](../AGENTS.md)의 공통 원칙을 실제 문항 작업에 적용하는 방법이며, 학교·과목별 소재와 금지 사항은 프로젝트 문서(인곽: [ishs/PROJECT.md](../ishs/PROJECT.md))에 둔다. 문항을 새로 쓰거나 고치기 전에 읽는다.

## 1. 출제 전에 사용자에게 묻기
- 새 문항을 만들거나 문항을 갈아엎을 때는 바로 쓰지 말고 **대안 2~4개를 먼저 제시**해 사용자가 고르게 한다. 대안마다 상황, 풀이 방식, 난도를 한두 줄로 적는다. 사용자가 "일단 다 만들어 보고 보여 달라"고 하면 그때는 바로 쓴다.
- 사용자가 정한 소재·장소·뼈대·번호는 바꾸지 않는다. 소재를 다른 장소로 옮기는 것도 대안으로 물어본 뒤에만 한다.
- 피드백이 준 범위만 고친다. 사용자가 좋다고 한 문항의 뼈대는 살린다.

## 2. 무엇을 낼까
- **소재는 수험생이 알아볼 수 있는 맥락에서** 고른다. 교과 문제에 상황 이름만 붙여 겉도는 문항은 피한다.
- **현실에 있는 일만 쓴다.** 실제 대상(봇·시설·제도·행사)에 없는 기능이나 관행을 지어내지 않는다. 행사·제도의 구조는 원문으로 확인한 실제를 쓰고, 퍼즐용 수치·규칙은 "~라고 하자"처럼 가정임이 드러나게 준다. 실제 사실과 가정을 한 문항에 섞으면 문장으로 구분한다. 대조하지 못한 법령·규정은 보고에 "원문 대조 필요"로 남긴다.
- 사용자가 요청한 가상 상황만 발문을 "다음은 가상의 상황이다."로 시작한다. 그 밖에 '(가상)' 꼬리표는 쓰지 않는다.
- 지문 일치·불일치나 말장난으로 푸는 "문과식" 문항보다 계산·배치·순서·참거짓·그래프 해석·짧은 코드처럼 생각해서 푸는 문항을 선호한다. 단, 사용자가 "문과적으로"라고 한 문항은 윤리·사상·정치와 법 같은 개념 추론으로 깊게 만든다(사상가 이름 없이 견해만으로 풀리게).
- 실명·학번·개인 사건은 쓰지 않는다. 사람은 갑·을·병·정·무 또는 A~C.

## 3. 조건과 난도
- **과조건 금지.** 대상 집단이 다 아는 사실을 조건으로 늘어놓지 않는다. 교과 공식·정의도 상자에 적지 않는다. 단, 사용자가 "교과 지식 없이 풀리게"라고 한 문항은 정의를 남긴다(지우기 전에 원래 지시를 확인).
- 풀이에 필요한데 상식이 아닌 사실은 자료로 준다.
- **조건은 짧고 쉬운 말로, 추론은 깊게.** 어렵게 만들 때 글을 길게 하거나 표를 읽기 어렵게 하지 않는다. 정보를 일부 숨기고 조건 하나로 순서·위치를 알아내게 하는 식으로 생각할 거리를 늘린다. 지문만 읽으면 답이 보이는 문항은 다시 쓴다.
- **자료가 풀이에 쓰여야 한다.** 이야기용 표·경과를 넣었으면 보기나 발문이 그 내용을 쓰게 만든다.
- 묻는 말의 핵심 동사(예: "오르내린 층 수")는 발문에만 쓰고 조건에는 쓰지 않는다.
- **발문은 짧게.** 상황 설명이 길면 자료 상자로 옮긴다. 길고 복잡한 한 문장은 한 줄짜리 항목 여러 개로 푼다.
- 개조식이 읽기 어려우면(포스터·안내문·그림 속 글) **문장으로 풀어 쓴다**. 주어 없는 문장("녹물을 채취하였다")은 누가 무엇을 했는지 쓴다.
- 같은 때의 여러 사건을 표로 줄 때는 왼쪽 '때' 칸만 세로로 합치고(md 표에서 칸에 `^`만 쓰면 위 칸과 합쳐진다) 오른쪽 내용은 한 행에 하나씩 둔다.
- **계산·퍼즐은 코드로 전수 검사**한다. 답이 하나인지, 오답이 각각 어떤 실수에서 나오는지 확인하고 적어 둔다. 날짜·요일은 실제 달력으로 확인한다. 검산 중에 드러난 모호함(읽는 규약 없음, 전제 누락, 정답이 둘)은 해설을 맞추지 말고 **문항 조건에 한 줄을 더해** 없앤다.

## 4. 형식과 배치
- 문항 수·배점·정답 분포는 프로젝트 설정을 따르고 `python -m examkit check`로 확인한다(이 검사는 풀이 정답을 보증하지 않는다).
- 한 문항이 다른 문항의 답을 흘리지 않게 한다. 같은 교시 안에서 수학 분야가 겹치지 않게 한다.
- **번호 배치:** 재밌는 문항을 앞번호에, 긴 킬러를 뒤에 둔다. 같은 행사·동아리·소재의 문항은 번호를 떨어뜨린다. 사용자가 고정한 번호(예: 20번 킬러)는 두고, 정답 번호가 3번 연속 같지 않게 본다. 순서를 바꾸면 `tools/reorder.py`를 문항 md와 해설 md에 같은 순서로 돌리고 사용자에게 새 번호를 표로 알린다.
- **쪽수는 억지로 맞추지 않는다.** 조건을 뭉개거나 글자를 줄여 목표 쪽수에 넣지 않는다. 넘치면 짝수 쪽으로 하고 단마다 여백을 고르게 한다. 줄이는 수단과 도구는 [HWPX 배치 노트](hwpx-layout-notes.md) 7절.
- 선택지가 짧으면 한 줄, 길면 세로. `@status`는 사용자가 마지막으로 본 판 대비 keep/mod/new.

## 5. 시각 자료 고르기와 역할 분담
- 문항에서 무엇을 읽고 판단해야 하는지 먼저 정하고 형식을 고른다. 인물 삽화만 생각하지 말고 공지·일정표·기사·메신저·SNS 게시물·기록표·사물·건물 단면·지도·도식·그래프를 함께 본다. 같은 형식(특히 인물 대화)이 시험지에서 반복되지 않게 한다.
- 글만 있어 허전하거나 단 아래 여백이 많이 남는 문항은 그림을 넣을 자리로 본다. 그림 폭은 보통 72~100mm.

| 누가 | 무엇을 |
|---|---|
| 이미지 생성 AI(ChatGPT 등) | 그림 요소가 조금이라도 있는 모든 것: 인물·사물·장면과 안내판·신문·메신저·SNS·재생 목록·건물 단면 같은 **자료의 틀**. 글자·숫자는 하나도 그리지 않고 글 자리는 흰 빈 판으로 남긴다. 요청 방법은 [삽화 요청서](illustration-request.md). |
| 코드(matplotlib 등) | 값·개수·연결 관계가 정답을 좌우하는 그래프·격자·조직도·배관도. 소스는 `assets/illust/sources/`. |
| 문서 작업 AI | 모든 글자(제목·표·대사·이름표·수치)를 글상자·표·말풍선으로 빈 판 위에 얹는다. 문항 작성·수정, 쪽 맞추기, 빌드, 렌더 확인. 그림이 든 자료를 HTML·합성으로 직접 그리지 않는다(`examkit/materials.py`는 시안용). |

- 생성 AI가 그린 글자는 오타가 잦고 고칠 수 없다. 정답 단서가 되는 글자는 반드시 문서 쪽에서 쓴다.
- 사용자가 준 사진(프로필 등)은 틀의 빈 자리 크기에 맞춰 합성해도 된다. 원본은 두고 합성본은 다른 이름(`…p.png`)으로 저장한다.

## 6. 여러 작업자(AI)로 나눌 때
- 문항 쓰기·해설 쓰기는 묶음별로 병렬로 맡기되, **교시 md는 직접 고치지 말고** 새 원문을 따로 저장하게 한 뒤 한 사람이 끼워 넣는다.
- 맡길 때 사용자 피드백 원문, 유지할 정답 번호·배점, 그림 좌표, 검증(파이썬 전수 검사) 요구, 렌더 확인 방법을 함께 준다.
- 돌아온 보고는 그대로 믿지 말고 끼워 넣은 뒤 직접 빌드·잘라 보기로 확인한다. 특히 작업자가 "지웠다"는 조건이 사용자 지시와 어긋나지 않는지 본다.
- 해설은 교시마다 한 작업자가 쓰되 모든 수치·논리 문항을 다시 풀어 `@answer`와 대조하게 한다.
